# 軟體設計原則與取捨

從 trade_engine 架構討論萃取，不含業務知識；例子只用來說明。已經過一輪對抗式審查（2026-11-04）。

## 一、模組與接口邊界

### 1. 依維度切模組，不依功能名稱切
委託管理處理「一次請求」：生命短、跨多筆委託、只留索引。委託狀態機處理「一個實體的一生」：生命長、持有可變狀態。判斷要不要拆看四件事：狀態歸誰、變更頻率、執行緒歸屬、測試方式。
- 代價：多一個交接介面。

### 2. 決策當下就把依據寫在實體上，之後不重算
路由結果在建單時寫進不可變的注記，撤單、改單照注記走，不重查路由表；否則配置一改，還在場的實體會被送到別處。
- 一般化：依賴可變配置的決策，要在決策當下把結果記下來。

### 3. 事實與決策分開，決策方不能否決事實
引擎只回報「成交了多少」「簿上發生了什麼」，狀態由狀態機決定。成交已經發生，狀態機若「不允許」，兩邊就對不上，所以決策函數必須是全函數。
- 不合法的組合視為上游 bug：事實照收（成交量、部位照記），只把該實體標成異常並告警，之後對它的請求一律拒絕，其他實體照常運作。決策函數對每個（狀態, 事件）組合都有定義，包括這個異常狀態。
- 角色分工：引擎是委託簿的唯一寫者，負責產生事實；狀態機是事實的投影，不是第二個裁決者（見第 6 條）。

### 4. 擁有與使用分開，跨模組順序交給組裝根
EngineManager 擁有引擎，OMS 只拿到唯讀的查找介面。物件圖在組裝根組起來；跨模組的啟停順序（例如回放完才開門收單）也由它負責。
- 順序要以「就緒訊號」為準（回放完成事件或 latch），不能以 `start()` 返回為準：核心跑在自己的執行緒上時，`start()` 通常一啟動執行緒就返回，回放還沒做完。
- 畫圖時，包含代表擁有，箭頭代表透過介面使用。

### 5. 定義抽象的接口範圍：所有實作都一樣的才放進共同契約
Gateway 的接口範圍是會話身分、請求進、回應與推送出。
- 傳輸層的握手、心跳、序號、補發屬於各協議自己（FIX 有 ResendRequest，WS 沒有，Kafka 靠消費端 offset），留在實作內。SessionKey 原本用 FIX 的 CompID，就是把單一協議的概念漏進了共同契約。
- 業務層的冪等鍵（例如以 (session, client order id) 去重）放進共同契約，因為每種協議都會產生重送：FIX 補發帶 PossDupFlag，WS 客戶端斷線後整張單重送，Kafka 是 at-least-once。
- 形狀不同的契約分開抽象：委託是請求/回應，行情是訂閱/推送，各自一個接口。
- 找邊界的方法：拿第二、第三個實作逐項比對。
- 取捨：契約越窄，各實作重複的東西越多；契約越寬，越容易被某一個實作綁死。

## 二、並發模型

### 6. 先選並發模型，其他規則都是它的推論

| 面向 | 單一寫者 + 訊息傳遞（LMAX） | 共享記憶體 + 鎖 |
|---|---|---|
| 保序 | 程式順序，不需要額外協定 | 靠鎖的範圍與取得順序 |
| 一致性 | 只有寫者改狀態 | 每個共享結構都要鎖 |
| 測試 | 同一串輸入 → 同一串輸出，可重放（前提：處理函數只依賴狀態與輸入；不以指標排序或迭代、不依賴 unordered 容器的迭代順序、不讀時鐘、不讀未初始化記憶體） | 時序相依，難重現 |
| 主要風險 | 單核上限、佇列塞滿 | 死鎖、鎖競爭、check-then-act 的 race |
| 擴展 | 依鍵切分成多個寫者 | 縮小鎖粒度 |

選了單一寫者，才有下面這些規則；走共享記憶體加鎖，這些不成立，換成鎖粒度、鎖順序與 race 的問題。
- 每份狀態只有一個寫者，其他元件送訊息請它改，裁決由寫者做。副本只能做「單調性質」的預檢（例如已終結的委託不會復活，可以直接拒絕撤單），其餘一律交給寫者判定。
- 跨執行緒只傳訊息，同一執行緒內才用函式呼叫。訊息定長、不含指標，編譯期檢查：`static_assert(std::is_trivially_copyable<T>::value && std::is_standard_layout<T>::value, "")`（C++14 寫法；`is_trivially_copyable` 擋不住裸指標，要靠「不含指標」這條規則）。
- 要落盤的訊息另加：`static_assert(sizeof(T) == N)`、固定寬度整數、padding 寫成明確欄位並在建構時清零、frame 帶版本號。否則改版後讀不回舊檔，逐位元組比對也會被 padding 裡的垃圾干擾。
- 擴展：讓最常一起改的狀態落在同一個寫者。一定還有別的關聯會跨寫者（例如委託簿按商品聚、保證金按帳戶聚），跨寫者的限制由持有該資源的寫者以「保留 → 確認 / 釋放」處理，接受多一跳延遲。
- 要量利用率。

### 7. 時間是輸入，不是環境
業務時間由單一入口打戳，打下的值要記下來，重放只用記錄的值。
- 單調鐘只用來在單一行程內量間隔，不跨重啟、不跨主機持久化：它的起點每次開機、每台主機都不同，開機 40 天後重啟，記錄裡的時戳約 3.5×10^15 ns，新事件卻從約 10^10 ns 起算。
- 牆鐘透過 (mono, realtime) 基準對換算；基準對在啟動與每次重新校準時以事件記錄，不要只在開機時取一次（NTP 可能還沒同步）。
- 沒有輸入時，用定時 tick 事件推進時間，tick 也要記錄。
- 反例：用 `CLOCK_REALTIME` 再取 max，時鐘往回撥 0.5 s，100 ms 的延時就變成 600 ms。

### 8. 非關鍵的消費者不能拖垮關鍵路徑
DB 副本若接在核心的輸出佇列上，主節點切換就能把佇列塞滿，讓核心停下；共用同一條佇列就是同生共死。解法是換介質解耦（副本改讀 Journal 檔），慢的 session 自己斷線。
- 非關鍵消費者的緩衝：容量 ≥ λ_peak × T，T 取 client 端的實際逾時，不是選主時間（例：MongoDB 選主中位數不超過約 12 s，但 driver 預設 `serverSelectionTimeoutMS` 是 30 s）。
- 追趕：停頓結束時積壓 B = λT，追完要 B / (μ − λ)，μ 要明顯大於 λ。例：λ = 50k/s、μ = 55k/s、T = 20 s，積壓 1M 筆，要 200 s 才追完，期間再出一次事就會塞滿。超過容量時怎麼處置要事先定好。
- 關鍵路徑的輸入佇列不照這個算：保持小容量，滿了就拒絕，不要讓請求在佇列裡等 20 s。

## 三、持久化與恢復

### 9. Journal 是服務自己的唯一正確來源，DB 是可回補的投影
- **先決定記輸入還是記輸出。**
  - 記輸入（LMAX 的做法）：恢復靠重跑。邏輯必須確定性，重放要用同版程式與配置，升版前先做 snapshot。
  - 記輸出：恢復靠套用。不依賴確定性，但每筆輸出都要落盤，寫入量大。
- **原子單位**：一筆輸入產生的所有記錄包成一個帶長度與 CRC 的 frame；恢復時截掉尾端不完整或 CRC 不符的 frame。
- **可見性**：只有「對外送出前先落盤（可 group commit）」才算 WAL 語意。不等落盤就不能叫 WAL，要寫明遺失窗口與對帳補救方式。
- **下游**：所有讀 Journal 的消費者（DB 投影、副本）只能讀到 journaler 公告的「已 fsync 位置」為止；否則 DB 會比唯一正確來源多出資料，而且沒有工具會發現。fsync 回錯就直接停機，不重試（PostgreSQL 2018 年的 fsyncgate：重試可能回報成功，資料卻已經丟了）。
- **和中介軟體脫鉤**：DB 不可用時，服務照跑；DB 恢復後從 Journal 回補。回補要成立，讀取位置要持久化、寫入要冪等（例如以流號 upsert）。
- 取捨：本地磁碟變成單點，主機整台掛掉 Journal 就一起沒了。要再往上一層就得做複寫：LMAX 是把輸入事件廣播給備機重跑；記輸出的設計則是把輸出 frame 送到備機套用。

### 10. 異常處理：多步驟操作逐步問「第 k 步和第 k+1 步之間當機會怎樣」
這次審查的兩個阻擋項都在這裡：三筆事件只寫進兩筆；請求還沒處理，入站序號就先推進。正常流程通常寫得完整，規格最薄的是失敗路徑。
- 連帶要寫明回放規則，例如成交量以成交事件的累計量為準，不看最後一筆狀態。

## 四、重構與流程

### 11. 重構舊系統：預設對齊舊行為
超出舊系統的部分列成標記項，附上不做的風險，之後再決定。
- 好處：範圍可控，並跑比對有基準；刻意的差異要先列白名單。
- 代價：明知地繼承舊風險，所以要寫下來。

### 12. AI 時代的審查：對抗式審查
找沒參與討論的審查者，要求每條發現對應到文字、附上「什麼輸入 → 什麼錯誤結果」，逐條核對才採用。
- 檢查技巧：先確認規則的前提會不會成立。例如唯一索引下不可能同分，「同分取 Priority」就是死規則。
- 這份清單的第一版就被抓出：把 LMAX 的「記輸入」Journal 和這次設計的「記輸出」Journal 混為一談，還借用了 WAL 的名字。

## 次要但值得記
- **先量再訂預算**：用固定速率（開迴路）送壓，延遲從「預定送出時間」起算，避免 coordinated omission；看完整百分位到最大值，並按事件種類分開，不看平均。閉迴路壓測時核心停 200 ms 只會記成一個慢樣本，以 10k/s 計，那段時間本該送出的約 2000 筆全被漏掉。
- **不要重用改了語意的名字**：舊 log 的 MATCH 指擬合，新設計指撮合，查問題時一定混淆。
- **第一階段最容易被低估的是基礎建設**：session 層、比對工具、部署設定。
