# 執行緒模型備忘錄

個人備忘錄，不是給 AI 讀的規範。用途：設計新模組、或線上出現非預期行為時，回頭對照這份重新定錨。

前身是 Architecture Playbook（2026-10 改寫）。物件分類（Calculator / Handler / Manager / Updater / DTO）改為命名慣例，見文末；原本的範例經驗保留在第三節。

---

## 一、判斷順序

拿到一筆可變狀態，依序回答，答案決定它落在哪個模式。鎖的種類是最後一欄的結論，不是第一個問題。

1. **寫者是誰**：哪條執行緒改它？只能有一個。有兩個名字就是設計問題。
2. **讀者有幾個、在哪**：同執行緒讀不用同步；跨執行緒讀才進下面的問題。
3. **一致性要求**：讀者能接受舊值？要跟另一筆資料同一時刻？寫完要立刻讀得到？
4. **多急**：熱路徑（行情 fan-out）、業務路徑（委託）、背景（落庫、統計）。
5. **生命週期**：舊版本被換掉後誰回收？讀者握著指標時物件會不會消失？
6. **背壓**：生產者快過消費者時，佇列長度誰管、滿了丟誰？
7. **半途失敗**：持鎖時 throw、事件處理到一半 crash，狀態停在哪？
8. **重入**：callback 會不會回頭呼叫發出它的模組？
9. **時間所有權**：timer 回呼跑在哪條執行緒？這會不會變成第二個寫者？
10. **啟停順序**：執行緒起來時資料就緒了嗎？關閉時佇列要排空嗎？

前四題決定模式，後六題決定模式之外還要補什麼。

## 二、模式表

| 場景 | 解法 | 主要風險 | 我們哪裡用了 |
|---|---|---|---|
| 可變業務狀態（持倉、委託、狀態機） | 單寫者執行緒 + 事件送入 | 跨執行緒查詢要走事件或快照 | 風控 Updater 群（部分） |
| 讀多寫少的大資料（配置、行情快照） | 不可變快照 + 指標交換 | 舊版本回收時機 | 風控 ConfigUpdater、QuoteHandler（目前是寫鎖） |
| 1:1 熱路徑 | SPSC ring，不走 EventBus | 無背壓就是延遲炸彈 | 行情 relay |
| 按 key 分片、片內有序、片間平行 | hash(帳戶) → 固定 worker | 跨 key 操作打破模型 | 風控 8 執行緒池（按用戶分） |
| 阻塞 I/O 要結果回來 | 丟輔助執行緒池，完成後以事件送回擁有者 | 回來時擁有者狀態已變，要帶版本號 | DB 寫入執行緒、RPC 下單撤單 |
| 跨執行緒同步查詢 | 讀快照 / 送查詢事件等回覆 / 擁有者定期發布唯讀視圖 | read-your-writes 問題 | — |
| 一對多廣播、消費者快慢不一 | 每消費者一條佇列；慢的 conflate 或踢掉 | 共享佇列被最慢的拖垮 | WebSocket 推送 |
| 多寫者、低讀、最終一致 | 每執行緒分片計數，讀時聚合 | seq_cst atomic 在熱路徑製造 cache line 競爭 | metrics |
| 跨所有狀態的一致性聚合 | 世代（epoch）編號，聚合者只讀同世代 | 這才是 barrier 真正要解的問題 | 浮盈計算、資金匯總 |
| 多模組必須原子生效的變更 | 版本化配置，各模組在下個事件邊界採用 | 真原子等於 stop-the-world | 配置熱更新 |
| 共享資源單一所有者 | I/O 執行緒擁有 socket，其他人 post 請求 | 兩個執行緒直接寫同一 socket 會交錯封包 | 上手連線 |
| timer 與排程 | 擁有者執行緒自己跑 timer wheel | 獨立 timer 執行緒 = 多一個寫者 | 逾時撤單、心跳 |
| 快取與失效 | read-through + 單一失效路徑 | 記憶體沒有、DB 也沒有時的保底 | 交易系統查委託 |
| 多階段 pipeline、速率不同 | 有界佇列 + 明確丟棄策略 | 行情可丟、委託不可丟，同一條 pipeline 要兩種策略 | 行情解析 → 聚合 → 推送 |
| 優先權插隊 | 分車道（兩條佇列）而非優先佇列 | 優先佇列破壞同帳戶順序 | 撤單 vs 新單 |
| 跨進程共享 | 共享記憶體 ring + seqlock | 跨進程 mutex 在對方死掉時永不釋放 | 源頭機器 adapter ↔ relay |
| 可重放的確定性狀態 | 狀態機只吃事件，時間當事件注入 | handler 裡呼叫 now() 就不能重放 | — |

真正需要「協定」而不只是「結構」的只有兩列：跨 key 原子操作、全狀態一致聚合。這兩列才需要 ADR。

### 執行緒清單

| 執行緒 | 職責 | 節奏 |
|---|---|---|
| 主執行緒 | RiskManager 初始化、依賴注入、啟動 | 一次 |
| 7 條事件接收執行緒 | 各 Updater 收 kafka 並更新 | 事件驅動 |
| ProfitCalculator | 定時拉持倉 + 行情算浮盈；拉委託 + 行情更新最新價 | 定時 |
| 風控池（8 條） | 每 100ms 取全部用戶，分配計算保證金 / 資金匯總 / 規則判斷；全部算完才進下一輪 | 100ms + barrier |
| DB 寫入執行緒 | 定時將資金 / 持倉明細 / 持倉合計寫入 DB | 定時 |

### 核心任務流程（風控池每個 worker）

1. 向 UserAccountUpdater 確認是否有變更緩存，有就更新
2. 新建資金匯總物件（主帳戶維度），向 ConfigUpdater 取匯率
3. 向 UserPositionUpdater 取用戶持倉
4. 計算持倉保證金：檢查待平手數是否已處理（沒有就告警）→ 確認產品變更緩存 → 確認產品狀態可算 → 算 → 寫進資金匯總 → 持倉明細 / 合計進 DB 緩存
5. 向 UserOrderUpdater 取用戶委託
6. 計算委託保證金：同上，檢查的是已撤單
7. 匯總總保證金（主帳戶維度，持倉 + 委託）
8. 向 RiskRuleUpdater 取用戶規則，判斷觸發
   - 強平前先判斷有無委託：有就先撤單，下一輪再確認強平
   - 透過 RPC 向交易服務下單 / 撤單
   - 強平在持倉上加「待平手數」、撤單在委託上加「已發撤單」，避免重複觸發
9. 帳戶資金 / 主帳戶資金進 DB 緩存

### 事件回呼

- 交易事件 → UserPositionUpdater 更新 → 回呼 UserRiskHandler 標記要刪除的倉位，讓 DB 同步
- 用戶事件 → UserInfoUpdater 更新（含新增 / 刪除）→ 回呼 UserRiskHandler 標記要刪除的用戶

## 四、踩過的坑

- **記憶體查不到走 DB**：保底本身開了新戰場——DB 也查不到呢？任何視角都要有失敗處理，但保底會遞迴。
- **手刻讀寫鎖的寫優先**：前人用 mutex + condvar 實作，加寫優先避免寫飢餓。接手時不知道為什麼要有，後來理解是事件執行緒的寫入不能被 8 條讀者餓死。
- **barrier 等的不是「一起算完」**：是「同一輪看到同一份資料」。用 semaphore 實作 barrier 達成了前者，後者其實靠的是 100ms 內資料沒變的假設。
- **浮盈不是同世代**：ProfitCalculator 分兩次拉持倉和行情，兩次之間行情可能已更新。目前可接受，但要知道這是假設不是保證。

---

## 五、還沒驗證的判斷

- QuoteHandler / ConfigUpdater / RiskRuleUpdater 改成快照交換後，讀路徑能否完全無鎖
- 待平手數 / 已發撤單這兩個跨輪狀態，依賴「同一用戶每輪落在同一 worker」還是「寫回共享物件」——哪一種，決定它們是否需要同步
- 事件接收執行緒和風控池之間是否存在重入（Updater 回呼 UserRiskHandler 時，Handler 有沒有可能正在被 worker 讀）

## 附：命名慣例（原物件分類）

後綴帶類型，一眼看出職責：

- 業務物件：`*Calculator`（算數值）、`*Handler`（業務行為與驗證）、`*Manager`（組裝與依賴注入）、`*Controller`（對外窗口）
- 資源物件：`*Updater`（擁有資料物件，保證寫入與讀取的一致性和執行緒安全）、`*DTO`（格式轉換）
- 資料物件：貧血，只有欄位

原則保留兩條：業務物件不直接擁有資料物件，透過 Updater 的介面取得；業務物件向 Updater 註冊回呼完成事件導向溝通。其餘的分類學不用，領域模型（GLOSSARY）夠了。
