# 記憶體管理

本文聚焦在理解linux系統(Ubuntu 22.04)以及gcc 11的版本下，如何透過更有效的記憶體管理來優化程序的性能。

## 記憶體生命週期類型

應用程序的記憶體，依生命週期可以分為以下幾種：

1. **分配一次，永遠活著**  
   程序中的 main 函數、singleton 物件皆屬此類。  
   記憶體隨程序啟動而分配，隨程序結束才釋放。

2. **分配，用完，釋放**  
   業務物件的典型模式。C++ 中以 shared_ptr / unique_ptr  
   管理 ownership，決定何時釋放。  
   記憶體來源可以是 heap，也可以是 memory pool，  
   兩者描述的是不同維度：前者是「誰負責釋放」，後者是「從哪裡分配」。

3. **分配一次，反覆使用**  
   一次向系統申請一整塊記憶體，物件用完後歸還給 pool 而非 heap。  
   Object pool 和 memory pool 屬於此類，  
   目的是避免反覆向系統申請記憶體的開銷，以及避免heap導致記憶體出現碎片化(fragamentation)。

4. **固定容量，循環覆寫**  
   Ring buffer / circular buffer 屬於此類。  
   記憶體本身永遠活著（類似模式一），但其中的資料沒有明確的釋放動作，  
   而是在容量滿時被新資料直接覆蓋。  
   生命週期由空間壓力決定，而非由擁有者決定。  
   io_uring 的 registered buffer 也是這個概念的延伸。

## 場景討論

涉及到記憶體分配的場景，我認為有以下幾塊

1. **生命週期長，且被多個模組共享**  
   例：風控服務中的倉位物件。服務啟動時從交易服務拉取現有倉位並建立物件，  
   此後由多個模組（浮盈計算、風控檢查）共同讀取。除非收到交易服務的平倉通知，  
   否則物件與服務本身的生命週期同步。

2. **生命週期短，用完即棄**  
   例：網路層的封包物件。封包從 kernel 緩衝區送達 user space 後，  
   會被解析並轉換成服務內部的業務物件，原始封包結構在轉換完成後即可釋放，  
   底層緩衝區則被複用以接收下一個封包。
