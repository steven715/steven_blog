# 資料事件同步機制

在公司進行了一個針對原有風控系統的重構，過程中遇到了對資料同步間的處理困難，像是用戶持倉的數據同時會被計算浮盈的物件、計算止盈止損的物件、計算風控規則的物件等多個物件所使用，所以想針對類似的場景做一個探討，理出一個解決框架，好讓未來處理上能有一個依據，而不是每次遇到都有點手足無措。

## 相關場景羅列

1. 用戶持倉的數據同時會被計算浮盈的物件、計算止盈止損的物件、計算風控規則的物件等多個物件所使用，且用戶持倉物件還有可能因外部消息系統 (如: kafka) 的事件通知，而改變內部物件數據或是物件刪除。
   1. 依賴的物件會主動取得被依賴物件的數據，被依賴物件在過程中有可能異動。
2. 行情數據會被止盈止損物件、計算浮盈物件、計算價格預警物件所使用，所以這些業務物件都會用輪詢的方式向行情物件取數據。
   1. 依賴的物件會主動取得被依賴物件的數據，被依賴物件在過程中有可能異動。
3. 持倉物件上有產品物件的資訊，而產品物件會因外部消息系統的事件通知，而改變內部物件數據。
   1. 依賴的物件不會主動取得被依賴物件的數據，而被依賴物件在過程中有可能異動，但需要通知回去依賴的物件。

## 解決方案的思路

1. 可以發現當依賴物件主動取用被依賴物件數據的時候，不太需要關注資料的同步，因為每次取得的當下都是保證最新數據，所以這邊會是探討如何取資料能達到最優的性能，像是某一合約的行情數據有可能1秒內10次更新，行情物件更新數據的時候會將物件上鎖，這時取用行情的物件就會受到影響，且行情物件中會有多個合約，也就是有個合約列表，若行情處於頻繁更新，一秒3,4000多的數據，要讓依賴的物件不受影響的正常取用行情。
   1. 原方案是使用 **map<string, quote>** 這樣的數據結構存放最新行情，另外用一個 **map<string, list<quote>>** 存放行情區間列表，因為有物件會涉及到價格區間內的判斷，所以每一筆行情數據都需要捕捉到。
   2. 探討方向會是確認是否有更好的資料結構，來應對這樣的場景，所以會先依原數據結構看當前性能瓶頸，再實作測試方案去比對性能差異。
2. 依賴的物件不主動取得被依賴物件，所以被依賴物件需要再改動的時候，能有一個同步機制讓依賴物件知道資料更新。
   1. 原先的機制是被依賴物件會拆分成緩存類跟更新類，而依賴物件是主動取用被依賴物件數據的，不過他是向緩存物件要的資料，接收消息的更新類再更新完後，會透過物件函數的調用，將數據同步給緩存類。
   2. 探討方向是看原先的機制，能否透過觀察者模式或是內部的eventbus相關機制來做優化，因為上面那種寫法實務上會覺得有點過度重複。

## 鎖策略

資料同步機制大致有以下幾類，能夠針對場景下去混搭

1. 互斥鎖 (Mutex): 同時只有一人進入臨界點，最簡單實現一致性
2. 自旋鎖（Spin Lock）: 取鎖失敗時不 sleep 而是空轉等待，適合臨界區極短且競爭極低的場景，競爭高時反而比 mutex 慢
3. 讀寫鎖（RW Lock）: 共享讀、互斥寫，適合讀多寫少場景，寫者要等讀者，注意：讀者過多可能造成寫者飢餓，可透過寫者優先機制解決（有寫者等待時，禁止新讀者進入）
4. 順序鎖（SeqLock）: 用 sequence 數字的奇偶標記「寫入中」，寫者不等讀者，直接寫；讀者若偵測到寫入中則重試，適合多欄位需要一致性、寫入時間極短的場景
5. RCU（Read-Copy-Update）: 寫者複製新版本修改後，用原子指標切換，讀者完全零阻塞，但舊版本必須等所有舊讀者完成後才能釋放（Grace Period），實作最複雜

```docker

# 更新並安裝必要工具
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential \
        git \
        clang-format \
        cppcheck \
        aspell \
        colordiff \
        vim \
        curl \
        gdb \
        htop \
        iproute2 \
        iputils-ping \

    rm -rf /var/lib/apt/lists/*

    apt-get install -y curl ca-certificates && \
    cd /usr/local/src && \
    curl -LO https://github.com/Kitware/CMake/releases/download/v3.22.2/cmake-3.22.2-linux-x86_64.tar.gz && \
    tar -xvf cmake-3.22.2-linux-x86_64.tar.gz && \
    mv cmake-3.22.2-linux-x86_64 /usr/local/cmake

# 設定 CMake 到 PATH（對所有 shell 生效）

# 安裝 vcpkg

RUN git clone https://github.com/microsoft/vcpkg.git && \
    cd vcpkg && \
    ./bootstrap-vcpkg.sh -disableMetrics

ENV PATH="${VCPKG_ROOT}:${PATH}"
```

## 問題場景 - 輪詢場景下嵌套類型共享資料的同步處理

當前有N個業務物件，同時去讀一個資源物件裡的共享資源，資源物件會負責這個共享資源的寫，讀跟寫都以多執行緒的方式

假設這N個業務物件平均以 10 ms去讀這這個共享資源，並且實際的寫是針對共享資源下面的map的element，可能會有新增、刪除、修改等行為，該element更新後還會對另一個統計的map做更改

要基於這個假設下提供一個線程安全又高效的同步機制

```cpp
// 共享資源性質定義
struct SharedObj
{
   map<string, realObj> details;
   map<string, calObj> totals;
};

map<string, sharedObj> objects;
```

## 解決方案

- 透過讀寫鎖，來將共享讀跟互斥寫的兩個行為分開
- 共享資源下的實際物件，也就是map中嵌套另一個map，內層map需要對外提供線程安全遍尋函數以及新增、修改、刪除等函數

## 問題場景 - 共享資料量大時避免阻塞

當前有N個業務物件，同時去讀一個資源物件裡的共享資源，資源物件會負責這個共享資源的寫，讀跟寫都以多執行緒的方式

假設這個資源物件每次寫入都是一個高I/O的操作，如何讓業務物件的使用延遲降低

## 解決方案

- 使用雙緩衝，讀資料跟寫資料
- 使用指針操作返回
- 寫資料跟讀資料交換只做指針交換

## 問題場景 - 事件驅動優化輪詢場景的觸發機制

*業務物件*會透過**輪詢方式**向*行情資源物件*取得所有合約最新行情，並向*倉位物件*與*資金物件*取得相關數據，計算*用戶角度*下*各主帳戶的倉位*情況(因最新價異動的浮盈)是否該處發風控規則。

- 假設場景如下
  - 輸入
    1. 行情: 合約維度
    2. 倉位: 主帳戶維度、合約維度、用戶維度
    3. 資金: 主帳戶維度、用戶維度
  - 計算
    1. 資金: 主帳戶維度、用戶維度
  - 結果
     1. 強平行為

## 解決方案

- 事件驅動的核心在於區分出通知者(行情物件)與被通知者(風控業務物件)，明確雙方之間的溝通機制(主動或是被動通知)
- 被通知者(風控業務物件)只要將業務行為(判斷風控規則)與觸發方式(輪詢方式、訂閱方式)做出解耦
- 目標在於降低無效計算以增進性能

## 延伸議題

- 當用戶量龐大、倉位數量龐大、合約數量龐大，遇到高頻行情場景(股市開、收盤或是行情高峰期)，如何讓事件驅動能否比輪詢場景優秀
