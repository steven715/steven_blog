# 網路庫性能評測框架
## 從陳碩《Linux 多線程服務端編程》歸納

> 核心目的：建立一套可重複套用於任何網路庫或硬體環境的測試規範，  
> 而非記錄特定庫的數據（數據隨時可查，思考框架才是資產）。

---

## 一、核心認知：性能不是單一維度

評測一個網路庫之前，必須先確認你在意的是哪個維度，因為**同一個庫在不同維度上可能截然相反**：

```
吞吐量高   ≠   延遲低
延遲穩定   ≠   高並發下仍穩定
單線程快   ≠   多線程線性擴展
```

三個核心維度，互相不能替代：

| 維度 | 衡量的是什麼 | 典型關心場景 |
|------|------------|------------|
| **吞吐量 Throughput** | 單位時間能搬多少資料 | 文件傳輸、行情分發、串流 |
| **延遲 Latency** | 一次操作從發出到回應的時間 | 交易系統、即時控制、遊戲 |
| **事件處理效率** | event loop dispatch 本身的 overhead | 高並發 idle 連線、訊號驅動場景 |

## 二、測試場景設計

### 2.1 吞吐量測試：Ping-Pong 協議

**設計邏輯：**
- Client 與 Server 都實作 echo
- TCP 連線建立後資料來回反射，不做任何業務處理
- 目的是讓網路庫本身成為唯一變數，排除業務邏輯干擾

**為什麼在同一台機器測？**
- 若用兩台機器，瓶頸會落在網路頻寬（如 GbE 的 110 MiB/s 上限），所有庫都跑出一樣的數字，失去對比意義
- 同機測試讓 CPU 資源成為競爭點，才能看出庫的效率差距

**關鍵參數（需系統性變化）：**

```
並發連線數：1 / 10 / 100 / 1000 / 10000
消息大小：  512B / 4KB / 16KB / 64KB / 256KB
線程數：    1 / 2 / 4 / 8（= CPU 核心數）
```

**觀察重點：**
- 固定線程數，隨並發連線數增加，吞吐量如何變化？
- 固定並發連線數，隨線程數增加，吞吐量是否線性擴展？
- 不同消息大小下，各庫的相對排名是否改變？（排名改變代表各有適合的場景）

---

### 2.2 事件處理效率測試：擊鼓傳花（Ring Benchmark）

**設計邏輯：**
- 建立 N 條連線首尾相接成環（pipe 或 socketpair）
- 一個 token 在環中轉 M 圈，計量總時間
- 排除 TCP 協議棧的影響，**單純測量 event loop 的 dispatch 效率**

**為什麼需要這個測試？**

Ping-pong 的吞吐量測試包含了 TCP 協議棧、buffer 管理等因素；  
擊鼓傳花把問題縮小到「一個 fd 上有事件，到 callback 被執行」這一步的 overhead。

**關鍵參數：**

```
總連線數（並發數）：100 / 1000 / 10000 / 30000 / 100000
活動連線數：       1% / 10% / 100%（全活躍）
```

**觀察重點：**
- 活動連線數固定，隨總連線數（idle fd）增加，效率如何退化？
- 這直接反映 `epoll` 在大量 fd 下的 `EPOLL_CTL_ADD` / `wait` overhead

**測試執行規範：**
- 多次循環取平均，捨去第一次熱身數據（避免 cold cache 污染結果）
- 分別記錄「含初始化」與「不含初始化」的時間，因為有些庫初始化成本高但穩態快

---

### 2.3 延遲測試：小訊息 RTT

**設計邏輯：**
- 送小訊息，統計 round-trip latency 分布
- 重點在**分布**，不是平均值

**為什麼不能只看平均值？**

```
P50  → 正常情況下的延遲基線
P99  → 系統偶發壓力下的表現（大多數用戶感受到的最差情況）
P999 → 極端情況（GC、context switch spike、OS jitter）
```

平均值會掩蓋尾延遲問題。一個 P50 很好但 P999 很爛的庫，在金融場景是不可接受的。

**關鍵參數：**

```
消息大小：64B / 512B / 4KB / 16KB / 64KB
負載水平：空閑 / 50% 負載 / 90% 負載（測壓力下的延遲退化）
```

**觀察重點：**
- 消息大小增加時，延遲曲線在哪個點開始急劇上升？
- 高負載下 P99/P999 相對 P50 的倍數（倍數越小代表越穩定）

**注意 Coordinated Omission 問題：**
- 傳統測試工具在 server 慢時會「等待」，導致低估尾延遲
- 應使用 `wrk2` 或 `HdrHistogram` 的方式，按固定頻率發送請求，不等前一個完成

---

### 2.4 多核擴展性測試

**設計邏輯：**
- 固定並發連線數，逐步增加 worker thread 數
- 觀察吞吐量是否線性成長

**理想與現實：**

```
理想：2 thread = 2× 吞吐，4 thread = 4× 吞吐
現實：受限於鎖競爭、False sharing、io_service 單點等因素
```

**判斷標準：**
- 擴展效率 = 實測吞吐 / (單線程吞吐 × 線程數)
- > 80%：擴展性良好
- 50–80%：有鎖競爭或設計瓶頸，可接受
- < 50%：多線程設計有根本問題

**常見退化根因：**

| 退化現象 | 可能原因 |
|---------|---------|
| 2 thread 後不再成長 | 單一 event loop / io\_context 成為瓶頸 |
| 線程越多越慢 | False sharing、鎖競爭、context switch overhead |
| 特定並發數後才退化 | accept queue、epoll fd 爭用 |

## 三、對比維度矩陣

針對任意兩個庫 A 和 B，以下維度都應該分別測試：

```
                    單線程    多線程（=核心數）
                    ────────  ────────────────
低並發（< 100）     ✓         ✓
中並發（1000）      ✓         ✓
高並發（10000+）    ✓         ✓
```

並在每個格子裡分別量測：吞吐量、P50/P99 延遲、CPU 使用率。

**為什麼要同時變化並發數和線程數？**

因為某些庫在低並發多線程下表現好，在高並發單線程下卻差（或反之），交叉測試才能看出真正的適用場景邊界。

## 四、根因追蹤原則

**數字本身不是結論，根因才是。**

拿到性能差距後，必須問：

```
差距是設計決策造成的，還是實作缺陷？
  ↓
設計決策 → 這個決策是針對特定場景的 trade-off，不代表庫「差」
實作缺陷 → 有可能被修復，不代表設計有問題
```

**追蹤工具：**

```bash
# 確認瓶頸在哪一層
perf stat -e cache-misses,context-switches ./benchmark

# 看 syscall 分布
strace -c -e trace=network ./benchmark

# 生成 flamegraph 找熱點
perf record -F 999 -g ./benchmark && perf script | flamegraph.pl > out.svg
```

**常見根因類型：**

| 根因類型 | 典型例子 | 影響的測試場景 |
|---------|---------|-------------|
| 每次讀取的 buffer 大小限制 | `read()` 上限太小，syscall 次數多 | 大消息吞吐量 |
| 單一 event loop 競爭 | 所有線程共用一個 `io_context` | 多線程擴展性 |
| 初始化開銷高 | `EPOLL_CTL_ADD` 在大量 fd 下慢 | 高並發初始化 |
| 協議層 overhead | 消息格式、路由層、加密 | 小訊息延遲 |
| Lock contention | 共享資料結構上的鎖 | 多線程高並發 |

## 五、測試執行規範

### 環境控制

```bash
# 固定 CPU 頻率，避免 DVFS 干擾
sudo cpupower frequency-set -g performance

# 綁定進程到特定 CPU，避免 NUMA 影響
taskset -c 0-3 ./server &
taskset -c 4-7 ./client &

# 調整 fd 上限
ulimit -n 1000000
```

### 編譯規範
- 所有對比庫使用相同的優化參數（如 `-O2`）
- 記錄確切的版本號與 commit hash
- Release build，關閉 debug 符號

### 數據採集規範

```
每個測試點：
  熱身：至少 1 次，數據捨棄
  正式：至少 5 次，取平均
  記錄：mean + stddev + P50 + P99 + P999
  
避免：
  只跑一次就下結論
  只記錄最好的一次
  不同測試點之間不重啟程序
```

### 結果呈現

- 用折線圖而非柱狀圖（因為 x 軸通常是連續的並發數）
- x 軸用對數刻度（1, 10, 100, 1000, 10000 跨度大）
- 同一張圖呈現多個庫，方便視覺對比

## 六、從測試數據到選庫決策

數據收集完後，用以下框架做決策：

**Step 1：確認你的場景屬性**

```
訊息大小？       小（< 1KB）→ 延遲敏感     大（> 64KB）→ 吞吐敏感
並發連線數？     少（< 100）→ 設計簡單優先  多（> 10K）→ 擴展性優先
線程模型？       單線程 loop →              多線程 →
業務特性？       CPU bound →                IO bound →
```

**Step 2：找出你場景下的最差數字**

選庫不選平均，選 **你的場景對應格子裡的 P99**。

**Step 3：追根因，判斷缺陷是否可修**

- 如果差距來自設計決策（如 proactor vs reactor），換庫
- 如果差距來自參數設定（如 buffer size），先調整再重測

**Step 4：加入非性能因素**

```
API 複雜度    → 維護成本
社群活躍度    → 問題能否得到解答
平台支援      → 是否要跨 OS
依賴項        → 引入的風險
```

性能只是選庫的其中一個維度，從來不是唯一標準。

## 七、快速測試 Checklist

每次評測一個新庫或新硬體，按以下順序進行：

```
□ 記錄測試環境（CPU、記憶體、OS、版本號）
□ 單線程 ping-pong，並發數 1/10/100/1000/10000
□ 多線程 ping-pong，並發 1000，線程 1/2/4/8
□ 小訊息延遲（64B），記錄 P50/P99/P999
□ 擊鼓傳花，總連線 100/1000/10000/100000
□ 長時間穩定性（30 分鐘），觀察是否有 latency 退化或 memory leak
□ 對每個顯著差距，追到源碼或 syscall 層的根因
□ 結論：適合哪些場景，不適合哪些場景
```
